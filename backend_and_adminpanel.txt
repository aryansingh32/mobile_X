Full Backend & Admin Panel Analysis — mobile_X
1. Backend Architecture
Framework: Express.js + TypeScript (Node.js), compiled with tsc.
Database: PostgreSQL via Prisma ORM (schema.prisma).
Cache / Queues: Redis (via ioredis / BullMQ). The queueService starts a BullMQ worker on import.
Entry point: backend/src/index.ts
Port: 5000 (default), 0.0.0.0 bind.

Middleware stack (in order):

express.json({ limit: '10kb' }) — payload size guard
cors — CORS_ALLOWED_ORIGINS env list
helmet — HTTP security headers
hpp — HTTP Parameter Pollution protection
globalLimiter — Express-rate-limit (securityMiddleware)
morgan — HTTP logging piped to Winston logger
fraudDetectionMiddleware — Redis-based multi-account + rate detection
promBundle (express-prom-bundle) — Prometheus metrics on every route
News ingestion: Cron job via node-cron, runs every 5 minutes (*/5 * * * *), calls runIngestionNow().

3. Telemetry Endpoint — The One Getting 500 Errors
Endpoint: POST /api/telemetry/track
File: backend/src/routes/telemetry.ts

What it does:

Accepts { eventType, count } in the body.
Updates lifetime user stats (e.g. lifetimeScreentimeMin, lifetimeNewsReads, lifetimeAdsWatched, etc.) in the User model.
Finds all active Missions with metricType === eventType.
For each mission, upserts UserMissions progress.
If mission completes (progress >= targetCount), runs a DB transaction:
Marks UserMissions.completedAt
Increments user.xp and user.totalCoinsEarned
Creates a CoinLedger entry with source: MISSION_COMPLETED_${mission.id}
Why it 500s:
The error is caught and returns 500 + "Failed to process telemetry". The likely cause is the metricType field on Missions — the telemetry handler queries prisma.missions.findMany({ where: { metricType: eventType } }). If the Missions table doesn't exist yet (seed not run), or if any mission has a missing/null metricType, Prisma will throw. Also: if lifetimeReferrals is sent as eventType, the code explicitly skips it (// We didn't add lifetimeReferrals to the Prisma schema, skip) but still tries to update user if other keys match — and if Object.keys(userUpdate).length > 0 the DB update runs, which should be fine. Most likely cause: migrations not run or seed-config not run, causing Prisma errors when querying the Missions table. The catch block swallows the actual error to console but returns 500.

5. Coin System — How Coins Are Granted in Backend
All coin grants go through addLedgerEntry() in services/ledgerService.ts:

Creates a CoinLedger row with amount, source, idempotencyKey, sessionId, deviceId, ipHash
Idempotency key format: ${source}:${userId}:${sessionId} — prevents double-claim
Shadow banned users get source: SHADOW_${source} (coins recorded but flagged)
Balance is always computed as SUM(amount) on CoinLedger (ledger pattern, no balance column)
Coin sources (all via CoinLedger.source):

Source	Granted by	Endpoint
AD_REWARDED	claimAdReward (adType=REWARDED)	POST /api/rewards/ad
AD_REWARDED_INTERSTITIAL	claimAdReward (adType=REWARDED_INTERSTITIAL)	same
AD_REWARDED_DISCOVER	claimAdReward (adType=REWARDED_DISCOVER)	same
SHORT_WATCH	claimShortReward	POST /api/rewards/shorts
ROULETTE_SPIN	claimRouletteSpin	POST /api/rewards/roulette-spin
ROULETTE_AD	roulette ad watch	(ROULETTE_AD source in ledger)
DAILY_BONUS	claimDailyBonus	POST /api/users/daily-bonus
MISSION_COMPLETED_${id}	telemetry mission completion	POST /api/telemetry/track
OFFERWALL_DEMO	demo task complete	POST /api/webhooks/offerwall/complete
OFFERWALL_POSTBACK	real offerwall webhook	POST /api/webhooks/offerwall/postback
ADMIN_ADJUSTMENT	admin manual	POST /api/admin/users/:userId/balance
WITHDRAWAL_REFUND	rejected withdrawal refund	POST /api/admin/withdrawals/:id/process
REFERRAL_TIER_1_BONUS / TIER_2 / TIER_3	referrer bonus on withdrawal approval	same
WITHDRAWAL (negative)	withdrawal debit	wallet controller
Ad reward flow (claimAdReward):

Look up AdRewardRule by adType
Look up DailyCapPolicy for tier DEFAULT
Enforce global daily ad count (globalAdCount >= maxAdsPerDay → 429)
Enforce per-type daily cap (typeAdCount >= dailyCapForType → 429)
Enforce global daily coin cap (earnedToday + coinsAwarded > maxCoinsPerDay → 429)
Enforce global cooldown (time since last any-type ad < minCooldownSeconds → 429 + FRAUD log)
Enforce per-type cooldown (time since last same-type ad < cooldownSeconds → 429 + FRAUD log)
Check device fingerprint for isRooted or isEmulator → 403 + FRAUD log
Call addLedgerEntry() with idempotency on adSessionId
Award XP via addExp() using xp_per_coin_ratio config
Increment user.totalCoinsEarned
6. Content Filtering Logic (Why Articles Without Images Are Removed)
The ingestion pipeline does NOT filter out articles without images at ingest time.
In newsIngestionService.ts, the image fetch logic:

First checks RSS media:content field
Then checks content:encoded for <img> tags
Falls back to scraping the article URL for og:image or twitter:image via cheerio (5s timeout)
If no image found, imageUrl = null — article is still saved with imageUrl: null
However, the frontend likely filters articles without images. Looking at rssService.ts (fetchNewsFromDb), the query does NOT filter by imageUrl IS NOT NULL. So all articles including imageless ones are returned. The filtering must be happening in the frontend display layer (not shown here), or the frontend explicitly drops articles where imageUrl is null.

The FeedSyncLog tracks imagesFailed and imagesFetched counts — these feed into the admin "PARTIAL" sync status when some images couldn't be fetched.

7. Short Video Tracking Endpoint
Endpoint: POST /api/shorts/watch
File: backend/src/controllers/shortsController.ts
Auth: Required

Logic:

Validates videoId (string) and watchSeconds (non-negative number)
Clamps watchSeconds to max 180 (security: never trust client value)
Checks Redis key shorts_watch_cooldown:{userId}:{videoId} with 30s TTL using NX (set-if-not-exists)
If already set → returns 200 with coinsEarned: 0, xpEarned: 0 (acknowledged but no reward)
Computes: coinsEarned = floor(watchSeconds/10) * 0 (currently 0 — coins disabled for watch time)
Computes: xpEarned = floor(watchSeconds/10) * 2 (2 XP per 10s watched)
Pushes WATCH_COMPLETED event to BullMQ queue for async processing
Returns immediately with computed values
Separate reward endpoint: POST /api/rewards/shorts (claimShortReward) — triggered when user explicitly claims, validates minWatchSeconds from AppConfig (default 8s), enforces 24h cooldown per video.

NATIVE → admob_android_native_ad_unit_id
NEWS_BANNER → admob_android_news_banner_ad_unit_id
Ad Event Pipeline (POST /api/config/ad-event):
Saves AdEvent rows: REQUESTED, LOADED, FAILED_TO_LOAD, SHOWN, CLICKED, EARNED_REWARD, DISMISSED, ABANDONED
Ad farming detection: Only for REWARDED ad types on DISMISSED/ABANDONED events
Computes rolling abandonment ratio in configurable window (default 60 min)
If abandonRatio >= 0.6 and sample >= 5: returns penaltyUntil timestamp (escalating penalty, 300–1800s)
If sample >= 10 and ratio >= 0.85: logs HIGH severity AD_FARMING_SUSPECTED fraud incident
Ad Analytics endpoints:
GET /api/admin/ad-analytics/funnel — counts by eventType grouped
GET /api/admin/ad-analytics/fill-rate — REQUESTED/LOADED/FAILED_TO_LOAD per adType with fill rate %
GET /api/admin/ad-analytics/revenue-estimate — total ad rewards + payout cost in INR
Daily Caps (enforced in claimAdReward):
Global: maxAdsPerDay, maxCoinsPerDay, minCooldownSeconds (from DailyCapPolicy tier=DEFAULT)
Per-type: dailyCapForType, cooldownSeconds (from AdRewardRule)
Fraud detection: cooldown violations → FraudIncident with AD_REWARD_TOO_FAST
Device check: rooted/emulator devices → FLAGGED_DEVICE_REWARD_CLAIM (403 blocked)
